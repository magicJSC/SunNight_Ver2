# SunNight 역기획서

**이동식 거점을 중심으로 탐색·제작·방어를 결합한 2D 생존 디펜스**

| 문서 정보 | 내용 |
|---|---|
| 작성일 | 2026-10-13 |
| 분석 기준 | 로컬 SunNight 프로젝트, HEAD `859ade93` |
| 엔진 | Unity `6000.5.10f1` |
| 문서 성격 | 소스 코드·씬·프리팹·ScriptableObject에 근거한 현행 역기획 |
| 확인 범위 | 자체 C# 파일 164개의 구조 조사 및 주요 기능 코드 검토, 게임 씬 5개 목록, 빌드 설정, 입력 정의, 아이템 20개, 제작법 6개, 주요 전투 프리팹과 웨이브 데이터 |

## 1. 프로젝트 요약

SunNight는 플레이어가 주변을 탐색해 재료를 확보하고, 타워 주변에 방어 시설을 배치한 뒤 몬스터의 공격을 막는 2D 게임이다. 타워를 마우스로 옮기고 다시 설치할 수 있으며, 타워를 특정 위치에 놓아 문을 여는 퍼즐과 방어 이벤트도 존재한다. 수동 캐릭터 조작과 자동 방어 시설 운용이 결합되어 있다.

현재 빌드 설정과 메인 메뉴에서 확인되는 주요 체험은 **튜토리얼 플레이**와 **독립 보스전**이다. 낮·밤 생존 루프, 제작·제련·요리, 상점, 저장, 네트워크의 코드가 존재하지만 완성도와 실제 연결 상태가 서로 다르다. 따라서 완성된 장기 생존 캠페인보다는, 핵심 조작과 전투 콘텐츠를 구성한 개발 중 프로토타입으로 해석하는 것이 적절하다.

### 1.1 기획 요소 재구성

| 구분 | 재구성한 내용 | 근거 수준 |
|---|---|---|
| 장르 | 2D 생존·탐색 + 제작 + 거점 디펜스 + 보스 액션 | 시스템 조합에 따른 해석 |
| 핵심 목표 | 플레이어와 타워를 유지하며 방어 이벤트 및 보스전을 돌파 | 피해·사망·웨이브·보스 코드 |
| 핵심 차별점 | 방어 시설이 연결된 타워의 재배치, 타워 위치를 활용한 퍼즐 | 타워/건설/퍼즐 코드 |
| 조작 기반 | 키보드·마우스 중심 | InputActions 및 직접 입력 코드 |
| 시점 | 2D 평면 이동, 플레이어 추적 카메라 | Rigidbody2D·타일맵·카메라 코드 |
| 주인공 단서 | 대화 데이터의 화자 이름은 ‘리암’ | TalkSO 데이터 |
| 세계관 단서 | 연구소, 로봇 제작자와 지도에 관한 대화 | Laboratory 대화 데이터 |
| 플랫폼 | 데스크톱 입력을 전제로 한 구성. 실제 배포 대상은 미확정 | 모바일·콘솔 출시를 단정할 근거 부족 |
| 플레이 인원 | 현재 검토한 플레이 흐름은 로컬 플레이어 1명을 중심으로 구성 | 멀티플레이 기반 코드는 별도 존재 |
| 대상 이용자 | 탐색·제작·방어 배치를 함께 즐기는 이용자 | 기획적 추론, 확정 타깃 자료 없음 |

수익 모델, 정식 출시 계획, 목표 플레이타임, 확정 스토리 전체, 서버 운영 정책은 프로젝트에서 확인하지 못했다.

### 1.2 문서의 상태 표기

- **구현 확인:** 해당 행동을 처리하는 코드 또는 실제 데이터가 존재한다. 실행 검증 완료를 뜻하지 않는다.
- **부분 구현:** 주요 구조는 있으나 데이터·입력·진입·종료 처리 등이 비어 있거나 일관되지 않다.
- **의도 추정:** 이름·데이터·구조를 조합해 재구성한 기획이다.
- **개선 제안:** 현행 명세와 분리한 후속 작업 제안이다.

## 2. 게임의 핵심 경험

### 2.1 반복 플레이 구조

**탐색 → 자원 수집 → 아이템 제작 → 거점 배치·이동 → 방어 전투 → 보상 획득 → 다음 준비**가 코드로부터 재구성되는 기본 루프다.

| 단계 | 플레이어 행동 | 제공되는 피드백 | 다음 단계에 미치는 영향 |
|---|---|---|---|
| 탐색 | 이동, 달리기, 상호작용 대상 탐색 | 이동 애니메이션, 대상 표시, 대화 | 자원과 이벤트 접근 |
| 수집 | 쓰레기 더미 조사, 드롭 아이템 획득 | 조사 게이지, 인벤토리 수량 변경 | 제작 재료 확보 |
| 제작 | 제작 목록에서 결과물 선택 후 제작 | 필요 재료, 제작 가능 여부, 효과음 | 방어 시설과 무기 확보 |
| 배치 | 타워 주변 타일에 건물 설치 | 초록/빨강 배치 가능 표시 | 방어선 구성 |
| 재배치 | 타워 이동 모드 진입, 위치 선택 | 타워 미리보기, 시설 반투명 처리 | 진로 확보·퍼즐·방어 위치 변경 |
| 전투 | 직접 공격, 자동 포탑 운용 | 체력 변화, 공격 연출, 몬스터 사망 | 웨이브 종료·코인 획득 |
| 진행 | 문 개방, 컷신, 보스전 | 대화·카메라·Timeline | 다음 콘텐츠 또는 메인 복귀 |

일반 생존 모드에서 이 루프가 여러 날에 걸쳐 안정적으로 반복되는지는 미검증이다. 튜토리얼과 보스전은 별도의 초기화 규칙을 사용하므로 장비가 연속 승계되는 캠페인으로 설명하면 안 된다.

### 2.2 플레이어가 판단해야 할 문제

1. 제한된 재료를 무기와 방어 시설 중 어디에 사용할 것인가.
2. 타워와 건물을 어디에 놓아 몬스터의 접근을 막을 것인가.
3. 직접 전투와 시설 운용을 어떻게 병행할 것인가.
4. 달리기와 음식 사용으로 이동 속도·허기를 어떻게 관리할 것인가.

이는 시스템에서 읽히는 선택 구조다. 실제 난이도와 선택의 균형은 테스트 자금, 미완성 아이템 및 허기 감소 규칙 때문에 아직 별도 검증이 필요하다.

## 3. 진입·씬·진행 구조

### 3.1 현행 진입 흐름

```text
MainScene
 ├─ Start → 전환 연출 3초 → TutorialScene
 ├─ Boss  → 전환 연출 3초 → Boss1
 ├─ Option → BGM/효과음 설정
 └─ Exit → 앱 종료

게임 중 메뉴 → 계속하기 / MainScene 복귀
타워 파괴 → GameOver 연출 → MainScene 복귀 경로
플레이어 사망 → 상태에 따라 부활 또는 GameOver 연출
보스 사망 → 사망 효과 + Timeline 생성
```

보스 사망 시 생성하는 Timeline과 메인 복귀를 지원하는 `BaseTimeline.GoToMain()`이 존재한다. 모든 사망·종료 연출의 실제 재생 연결은 플레이 검증 대상으로 남긴다.

### 3.2 씬 목록과 노출 범위

| 씬/구성 | 파일 존재 | 빌드 목록 | 해석 |
|---|---|---|---|
| MainScene | 있음 | 활성 | 시작·보스·설정·종료 메뉴 |
| TutorialScene | 있음 | 활성 | 기본 조작, 제작, 타워 활용, 방어 학습 |
| Boss1 | 있음 | 활성 | 독립 초기 장비를 지급하는 보스 체험 |
| GameScene | 있음 | 미등록 | 일반 생존 초기화 코드와 씬은 있으나 기본 메뉴 진입 경로 없음 |
| Chapter1 | 있음 | 미등록 | 추가 콘텐츠 씬 자산. 현행 캠페인 연결은 확정 불가 |
| LaboratoryScene | 스크립트 존재 | 미등록 | 검토한 게임 씬 폴더에 동일 이름 씬 없음. 연구소 대화 데이터는 존재 |

`Define.SceneType`과 실제 씬 구성도 완전히 일치하지 않는다. 예를 들어 Boss1은 문자열로 로드되며 해당 열거형에는 없다. 개발용 씬과 배포용 씬의 기준 정리가 필요하다. [S01, S02]

## 4. 조작 및 상호작용 명세

| 입력 | 정의된 행동 | 구현상 주의점 |
|---|---|---|
| W/A/S/D | 이동 | 대각선 방향 정규화, 조작 잠금 시 정지 |
| 왼쪽 Shift | 달리기 | 이동 속도 1.5배, 누르는 동안 허기 감소 |
| E | 인벤토리 토글 | 입력 정의 및 `OnShowInventory` 존재 |
| Q | 제작 UI 토글 | 입력 정의 및 `OnProduceUI` 존재 |
| 1~5 / 마우스 휠 | 퀵슬롯 선택 | 5칸 구조 |
| F | 주변 상호작용, 대화 진행, 시설 회수 | 여러 행동이 같은 키를 공유하므로 UI·대상 우선순위 검증 필요 |
| V | 타워 이동 모드 진입/취소 | 직접 입력 및 InputAction 콜백 둘 다 존재 |
| 마우스 왼쪽 | 공격·설치·타워 배치 확정·섭취 | 장비·모드에 따른 분기와 중복 실행 검증 필요 |
| Esc | 팝업 닫기·게임 메뉴 | 컷신에서는 길게 눌러 스킵하는 구조 |
| Tab | 지도 입력 정의 | 지도 표시 토글 구현을 확인하지 못해 완성 조작으로 간주하지 않음 |

플레이어 이동과 건설, 타워 이동에는 직접 키 확인 코드와 Input System이 함께 사용된다. 일부 행동은 프레임 단위 중복 방지 로직을 갖고 있다. 입력 정의만 존재하는 행동과 실제 프리팹 이벤트까지 연결된 행동을 구분해 테스트해야 한다. [S03]

상호작용 대상은 플레이어의 트리거 범위 안에서 수집하고, 가장 가까운 오브젝트를 선택한다. 선택된 오브젝트에 표시를 띄우며 F 입력 시작/해제 콜백을 연결한다. 쓰레기 더미는 버튼을 유지하며 게이지를 채우고, 중단 시 조작 잠금과 게이지를 해제한다. 완료한 더미는 다시 조사할 수 없도록 처리한다. [S04]

## 5. 플레이어·생존·실패 규칙

### 5.1 기본 수치

| 항목 | 현재 값 | 근거 및 해석 |
|---|---:|---|
| 플레이어 최대 체력 | 100 | Player 프리팹 |
| 최대 허기 | 30 | Player 프리팹 |
| 기본 이동 속도 | 5 | 월드 이동 수치 |
| 달리기 배율 | 1.5배 | 정상 기본값 기준 속도 7.5 |
| 달리기 허기 소비 | 초당 0.1 | `deltaTime / 10` |
| 자연 체력 회복 | 초당 0.05 | `deltaTime / 20`, 최대 체력으로 제한 |
| 저허기 판정 | 최대 허기의 1/7 이하 | 최대 30일 때 약 4.29 이하 |
| 저허기 감속 데이터 | 속도 ÷2 | Hunger BuffSO |
| 타워 최대 체력 | 500 | Tower 프리팹 |

기본 허기 감소용 코루틴에는 실제 감소 연산이 없다. 따라서 ‘가만히 있어도 지속적으로 배고파지는 생존 게임’은 현재 확인된 규칙이 아니다. 달리기 소비와 음식 회복은 구현되어 있다. [S05]

### 5.2 피해와 사망

- 체력은 0부터 최대 체력 사이로 제한한다. 피해 처리 후 0 이하이면 사망 이벤트를 발생시킨다.
- 플레이어 사망 시 플레이어를 비활성화하고 사망 UI를 생성한다.
- `isMovingTower == false`이면 `Die`, true이면 `GameOver` 애니메이션을 선택한다.
- 부활 메서드는 타워 아래 위치에 플레이어를 다시 활성화한다. 플레이어 재활성화 시 체력을 최대치로 설정한다.
- 타워 사망은 별도의 GameOver 처리와 타워를 향한 카메라 전환을 실행한다.
- 무덤 생성 코드는 주석 처리되어 있어 사망 시 장비를 무덤에서 되찾는 규칙을 확정할 수 없다.

**중요한 불일치:** 현재 `TowerMoveController`는 자체 `isMoving` 상태를 바꾸지만, 위 사망 분기에 쓰는 `Managers.Game.isMovingTower`와의 동기화가 확인되지 않는다. ‘타워 이동 중 사망하면 게임오버’는 분기 의도이며, 실제 입력 경로에서 성립하는지 추가 확인해야 한다. [S06]

## 6. 시간·낮밤·야간 방어

| 기준 | 코드 값 | 게임 시간 해석 |
|---|---:|---|
| 시간 초기화 | 330 | 05:30 |
| 경고 시작 | 1200 | 20:00 |
| 야간 시작 | 1290 | 21:30 |
| 날짜 증가 조건 | 1440 이상 | 24:00 이후 |
| 일반/튜토리얼 속도 | 2 | 실제 1초마다 게임 분 수치 2 증가 |

시간 속도 2가 유지되고 정지·리셋이 없다는 조건에서, 05:30부터 21:30까지는 실제 480초(8분)다. 이는 계산값이며 실측 플레이타임이 아니다.

시간 이벤트는 조명, 시간·날짜 UI, 야간 경고와 몬스터 스폰을 연결한다. 야간 웨이브는 `day - 1`을 데이터 범위 안으로 제한해 선택하며, 마지막 데이터 이후에는 마지막 웨이브를 재사용하는 구조다.

튜토리얼은 날짜를 0으로 설정하고 시간 오브젝트를 비활성화한다. `GetClock` 트리거에 진입하면 시간 오브젝트를 활성화하는 경로가 있다.

**현행 불완전성:** `TimeController` 자체에는 1440 도달 후 시간을 감산하거나 날짜 증가를 1회로 제한하는 코드가 없다. `UI_Time.Sleep()`이 시간을 330으로 돌리고 Sleep 애니메이션 이벤트도 존재하지만, 이것만으로 정상 일주기 반복을 보장할 수 없다. 날짜 증가가 프레임마다 반복되는지, 수면 상태가 언제 호출되는지 실행 검증이 필요하다. [S07]

## 7. 인벤토리·자원·경제

### 7.1 보관 및 선택

인벤토리는 **24칸**, 퀵슬롯은 **5칸**, 합계 29칸이다. 각 슬롯은 아이템 데이터와 수량을 보관하며, 아이템별 최대 중첩 수량을 사용한다. 선택한 퀵슬롯의 아이템 유형에 따라 도구·건설·소비 동작이 달라지는 구조다.

인벤토리와 핫바 UI, 슬롯 이동·드래그·아이템 설명·폐기 관련 클래스가 존재한다. 포화 인벤토리에서 획득·제작·회수 결과가 소실되거나 중복되는지는 별도 검증이 필요하다. 특히 일부 호출자는 `GetItem()`의 남은 수량 반환값을 처리하지 않는다.

### 7.2 자원 획득과 소비

| 유입 | 처리 | 소비/사용처 |
|---|---|---|
| 쓰레기 더미 | 1~100 난수와 누적 확률로 목록 중 보상 선택 | 제작 재료 |
| 몬스터 처치 | 확률 아이템 보상 + 설정된 코인 지급 | 제작·상점·업그레이드 |
| 월드 아이템 | 플레이어 충돌 시 인벤토리 획득 시도 | 보관·섭취·장착 |
| 시설 회수 | 시설을 아이템 1개로 환원 | 다른 위치에 재설치 |
| 제작 | 재료 차감 후 결과물 1개 지급 | 무기·시설 확보 |

`UI_Inventory` 초기화에는 코인을 **10,000으로 설정하는 코드**가 있다. 현재 경제 수치는 개발·테스트 조건의 영향을 받으므로 정식 밸런스로 해석하지 않는다. [S08]

## 8. 제작·제련·요리·상점

### 8.1 제작 규칙

제작 UI에서 결과물을 선택하면 재료 아이콘·수량과 제작 가능 여부를 표시한다. 재료 검색 대상은 인벤토리 24칸과 퀵슬롯 5칸이다. 제작에 성공하면 재료를 차감하고 결과물을 **1개** 지급하며 효과음을 재생한다.

현재 Player 프리팹의 제작 UI 참조는 `Resources_moved/UI/UI_Produce.prefab`과 연결된다. 해당 프리팹에 저장된 제작식은 다음과 같다.

| 결과물 | 재료 | 결과 수량 |
|---|---|---:|
| 대포 | 고철 5 | 1 |
| 고철벽 | 고철 1 | 1 |
| 용광로 | 철 2 + 석탄 6 | 1 |
| 쓰레기통 | 철 1 + 나무가지 5 | 1 |
| 알루미늄 배트 | 철 4 + 나무가지 1 | 1 |
| 뇌전탑 | 고철 5 | 1 |

제작 대기시간이나 제작 큐는 이 경로에 없다. 결과물 저장 공간 부족, 제작 중 재료 변경, 여러 슬롯에 분산된 재료 소비는 테스트해야 한다. [S10]

### 8.2 가공 시스템

| 기능 | 확인 내용 | 현행 판정 |
|---|---|---|
| 제련 | 용광로 상호작용, 제련 UI, 진행 게이지, 시간 완료 콜백 | 구조 구현. 자산별 변환 연결 검증 필요 |
| 요리 | 모닥불에 선택 아이템 투입, 동시 처리 수 제한, ItemBaker 처리 | 구조 구현. ItemSO의 bakeItem 연결 검증 필요 |
| 섭취 | 선택 아이템의 canEat 확인, 허기 회복, 수량 1 감소 | 코드 및 음식 데이터 확인 |
| 회복약 | Consume 호출 시 체력 20 회복 | 코드 존재. 아이템 정의·호출 연결 미완성 가능 |

ItemSO에는 제련·굽기 결과물과 시간이 정의되어 있으나 일부 자산에는 과거 필드명 `smeltedItem`, `bakeItemSO`가 남아 있다. 현재 필드명은 `smeltItem`, `bakeItem`이므로 파일 존재만으로 정상 가공 가능하다고 판단하지 않는다.

### 8.3 상점

상인 데이터는 코인 거래와 물물교환을 지원하며, 상품 후보에서 5개를 무작위 선택한다. 동일 상품이 중복 선택되는 것을 방지하는 코드는 없다. 거래별 수량과 교환 가능 횟수를 관리하고, 300초 타이머를 표시한다.

그러나 상인의 상호작용 연결 메서드가 비어 있고 UI 열기 코드가 주석 처리되어 있다. 타이머 만료도 로그 출력만 하므로 **정상 접근·자동 폐점이 완성된 상점으로 볼 수 없다.** 경제 확장용 부분 구현으로 분류한다. [S11]

## 9. 타워·건설·시설 관리

### 9.1 건설 규칙

건설은 타워의 Building 타일맵을 기준으로 한다. 사용 가능한 타일은 이미 시설이 있는 칸, 타워가 차지한 칸, 월드의 건설 금지 칸을 제외해 만든다. 마우스 위치를 셀 좌표로 변환하고, 가능하면 초록 계열, 불가능하면 빨강 계열로 표시한다.

설치 성공 시 해당 타일에 아이템의 `buildTile`을 설정하고 선택 슬롯 수량을 1 감소시킨다. 이미 시설이 있는 칸을 선택하면 시설 정보 UI를 띄우는 경로가 있다.

### 9.2 타워 이동 규칙

V로 이동 모드를 시작하면 플레이어 조작을 잠그고 타워를 마우스의 정수 좌표로 이동시킨다. 타워 충돌체와 부속 건물 충돌체를 해제하고 시설을 반투명하게 만든다. 설치 가능 여부는 타워의 2×2 영역과 건설 금지 타일의 충돌로 검사한다.

왼쪽 클릭으로 확정하거나 V로 취소해 기존 위치로 되돌아간다. 확정 후 건설 가능 영역을 다시 계산하고 시설의 표시와 충돌을 복원한다. 지형과 겹치는 부속 시설을 회수하는 처리도 있다.

**규칙 충돌:** 야간·방어 이벤트·보스전은 `canMoveTower = false`를 설정하지만 타워 이동 시작 코드는 이 값을 검사하지 않는다. 따라서 ‘전투 중 타워 이동 금지’는 의도만 확인되며 현행 강제 규칙으로 적을 수 없다. [S12]

### 9.3 시설 정보·회수·강화

시설 UI에는 이름, 체력, 공격력, 공격 주기, 사거리, 강화 비용과 재료가 표시된다. 회수는 시설을 아이템 1개로 돌려주고 타일을 삭제한다. 강화는 `nextLevelItem`이 존재하고 코인·재료 조건을 만족하면 상위 타일로 교체한다.

강화 재료 검색은 제작과 달리 일반 인벤토리 위주이며, 여러 슬롯에 걸친 차감과 실패 후 임시 목록 정리에 추가 검증이 필요하다. 강화 UI가 존재한다는 이유로 모든 시설에 완성된 성장 단계가 있다고 해석하지 않는다. [S13]

### 10.3 보스전 시작 상태

Boss1 씬에 들어가면 인벤토리와 퀵슬롯을 초기화하고 다음을 지급한다.

| 퀵슬롯 | 지급 아이템 | 수량 |
|---|---|---:|
| 1 | 고철벽 | 10 |
| 2 | 대포 | 5 |
| 3 | 뇌전탑 | 3 |
| 4 | 알루미늄 배트 | 1 |
| 5 | 비어 있음 | 0 |

플레이어 체력 100, 허기 30으로 설정한다. 이는 이전 씬의 성장 결과를 가져오는 방식이 아니라 독립 전투 체험용 초기화다.

### 10.4 보스전 진행

```text
StartBoss1Cut 종료
 → 1라운드: 무작위 종류 1마리 → 전멸 대기
 → 2라운드: 무작위 선택 3회, 각 1마리 → 전멸 대기
 → 3라운드: 선택한 종류 A 2마리 + B 3마리 → 전멸 대기
 → Boss1.StartBattle()
 → 3개 패턴 중 무작위 실행·반복
 → 보스 HP 소진 → 사망 연출/Timeline
```

각 라운드는 살아 있는 적 집합이 비었을 때 진행한다. 3라운드 두 종류는 후보가 둘 이상이면 구분해서 선택하며, 하나뿐이면 같은 종류를 재사용한다. 그룹 내부 복수 스폰은 1초 간격이지만, 2라운드의 1마리 그룹들 사이에 별도 1초 대기를 넣지는 않는다.

### 10.5 보스 패턴

| 패턴 | 코드에서 확인되는 동작 | 타이밍 |
|---|---|---|
| 1 | 좌·우·상단 중 위치 선택, 레이저, 에너지 폭탄 3개 | 준비 2초 → 레이저 3초 → 폭탄 생성 → 6초 대기 |
| 2 | Pattern2 애니메이션 재생, 관련 레이저 오브젝트 구성 | 애니메이션 4초 → Idle 2초; 실제 타격은 애니메이션 연결에 의존 |
| 3 | 상단 고정 위치에서 회전 레이저 | 준비 3초 → -30°에서 -140°로 5초 회전·공격 → 2초 대기 |

패턴은 매번 0~2 난수로 선택한다. 체력 비율에 따른 페이즈 구분은 이 코드에 없다. 전투 클리어 보상·다음 챕터 해금·점수 평가가 완성되었다고 볼 근거는 부족하다. [S16]

## 11. 튜토리얼·대화·연출

튜토리얼은 단일 `TutorialController`가 전체를 지휘하는 구조가 아니다. 해당 클래스는 비어 있고, 대화 트리거·퍼즐·방어 이벤트·컷신이 기능을 나누어 담당한다.

| 학습 주제 | 구현 단서 | 학습 목표 해석 |
|---|---|---|
| 주변 탐색 | FindHelp, interactHelp | 조사 대상 발견과 상호작용 |
| 인벤토리 | InvenHelp | 가방 속 장비 확인 |
| 제작 | ProduceHelp | 재료를 결과물로 전환 |
| 거점 방어 | TowerHelpWall | 안전한 위치와 방어 시설의 필요성 |
| 위치 이동 | LoadHelp | 탐색 공간 이동 |
| 타워 퍼즐 | TowerPuzzle | 타워를 트리거에 놓으면 문 개방 |
| 방어 실습 | DefenseEvent, StartButton | 타워가 준비 영역에 있으면 시작 가능, 적 처치 후 통로 개방 |

위 표는 학습 주제 목록이며 실제 씬 내 통과 순서를 확정한 목록은 아니다.

Timeline은 카메라와 조작 잠금, 대사·사운드·Transform 트랙을 다룬다. Esc를 일정 시간 유지해 스킵 게이지를 채우고 지정 시간으로 이동하는 코드가 있다. 연구소 대화는 리암이 로봇 제작자의 거처와 지도를 언급하지만, 전체 세계관과 사건의 원인을 임의로 보완하지 않았다. [S17]

### 13.2 실행 구조

`Managers`가 게임·인벤토리·UI·사운드·맵·네트워크·데이터 접근점을 제공한다. 씬 초기화 코드가 플레이어, 타워, 빌더, 조명, 시간 UI 등을 생성하고 이벤트를 연결한다. 자산 로딩은 Resources와 Addressables가 혼용되어 있다.

설치 패키지/라이브러리에는 URP 2D, Input System, Addressables, Cinemachine, Timeline, Newtonsoft.Json, DOTween, ParrelSync 등이 있다. 패키지 설치는 해당 기능의 완성을 의미하지 않는다.

| 폴더 | 역할 |
|---|---|
| Assets/2.Scenes | 게임 씬 |
| Assets/3.Scripts | 게임·UI·매니저·통신 코드 |

| Packages / ProjectSettings | 의존성·엔진·빌드 설정 |

### 13.3 저장

저장하려는 정보는 아이템, 수량, 체력, 허기와 좌표다. 날짜, 코인, 설치 시설 전체, 웨이브 진행, 이벤트 완료 상태는 현재 `PlayerDatas`에 포함되지 않는다.

또한 경로 문자열 결합에서 디렉터리와 파일을 혼동하며, 저장 위치를 디렉터리로 만든 뒤 같은 경로에 파일을 쓰려는 분기가 있다. 로드용 Resources 경로도 실제 `Resources/Item`과 다르다. 게임 메뉴의 저장 호출은 주석 처리되어 있다. 따라서 **이어하기·정상 저장은 현행 제공 기능으로 분류하지 않는다.** [S19]

### 13.4 네트워크

TCP 세션·커넥터·패킷·Protocol 계층과 로컬 인증 서버 호출 코드가 존재한다. Managers 초기화에서 네트워크 초기화를 호출하며, 로컬 인증 엔드포인트 응답 후 TCP 연결을 시도한다.

저장소에서 검토한 범위에는 완성된 로그인 화면, 서버 실행 구성, 룸 생성, 매칭, 플레이 동기화 검증 자료가 없다. 따라서 **멀티플레이 지원을 확정할 수 없으며 통신 기반 작업이 남아 있는 상태**로 적는다. 테스트 인증 값은 본 문서에 재수록하지 않았다. [S20]

## 15. 후속 기획 제안

이 절은 현행 구현에 대한 설명이 아니라 프로젝트를 정리하기 위한 제안이다.

### 15.1 먼저 확정할 게임의 범위

현재 연결이 명확한 **메인 → 튜토리얼 / 보스전**을 첫 시연 범위로 삼고, 일반 생존 캠페인을 별도 완성 목표로 나누는 것이 합리적이다. 저장·상점·멀티플레이까지 동시에 완성 대상으로 잡으면 현재 핵심 재미인 타워 배치와 방어 검증이 늦어질 수 있다.

### 15.2 정리 순서

1. **플레이 경로 안정화:** 대상 플랫폼 빌드, 튜토리얼 방어 종료, 보스 진입·사망·복귀 검증.
2. **공통 규칙 통일:** 타워 상태, 전투 중 이동 제한, F/클릭 우선순위, 사망·부활, 시간 순환 정의.
3. **콘텐츠 데이터 정리:** 사용 아이템과 미사용 초안 분리, 표시명·중첩·타입·가공 연결 보완, 제작·강화 재료 규칙 통일.
4. **밸런스 검증:** 테스트 코인 10,000과 보스 지급품을 명시적으로 관리하고, 실제 자원 획득량을 기준으로 제작 비용 검증.
5. **확장 기능 선택:** 저장 및 캠페인 연결을 먼저 할지, 상점·지도·네트워크를 먼저 할지 목표 버전에 맞춰 결정.

### 15.3 첫 검증 플레이의 합격 기준

| 시나리오 | 합격 기준 |
|---|---|
| 시작·종료 | 메인에서 각 모드 진입 및 메인 복귀 가능 |
| 기본 학습 | 외부 설명 없이 이동·수집·제작·설치·타워 이동을 수행 가능 |
| 경제 보존 | 수집·제작·회수·강화 후 기대 수량과 실제 수량이 일치 |
| 방어 이벤트 | 마지막 적을 빠르게 처치해도 문이 열리고 다음 진행 가능 |
| 보스전 | 1/3/5 라운드 종료 후 보스 시작, 3개 패턴과 사망 처리 확인 |

## 부록 B. 이 문서에서 확정하지 않은 사항

- 실제 플레이 가능한 전체 챕터 순서와 튜토리얼 종료 후 자동 이동 경로.
- 그래픽의 최종 품질·해상도·화면별 정확한 배치와 가독성.
- 모든 Addressables 참조·애니메이션 이벤트·씬 오버라이드의 런타임 정상 동작.
- 타워·몬스터별 실효 DPS, 평균 클리어 시간, 난이도와 자원 밸런스.
- 멀티플레이 완성 여부, 서버 운영 방식, 정식 저장 정책.
- 최종 출시 플랫폼, 이용 등급, 수익화, 배포 일정.

코드와 설정에서 확인되지 않은 사항을 임의의 확정 기획으로 채우지 않았다. 실제 플레이 검증을 추가하면 본 문서를 화면 캡처와 검증 결과가 포함된 다음 버전으로 확장할 수 있다.
